# RAG 原理笔记

结合本项目的代码讲 RAG。每一节末尾标了对应的代码位置。

## 0. RAG 要解决什么问题

大模型有两个硬伤：

- **不知道你的私有资料**：公司制度、产品手册、个人笔记，训练时都没见过；
- **知识有截止日期**，而且不知道的时候可能会一本正经地编。

最直接的办法是把资料整个塞进 Prompt。但资料一多就塞不下，就算塞得下也又贵又慢，无关内容还会干扰模型。

**RAG（Retrieval-Augmented Generation，检索增强生成）** 的思路：先从资料库里**检索**出和问题最相关的几小段，再把这几段和问题一起交给模型**生成**回答。相当于让模型"开卷考试"，而且只翻相关的那几页。

```
        ┌──────────────── 离线：建索引（文档变了才重跑）────────────────┐
文档 ──→ ① 加载 ──→ ② 切块 ──→ ③ 向量化 ──→ 向量库
                                                 │
        ┌──────────────── 在线：每次提问 ──────────┼───────────────────┐
问题 ──→ ③ 向量化（同一个模型）──→ ④ 相似度检索 top_k ──→ ⑤ 拼 Prompt ──→ Claude ──→ 回答
```

本项目的示例知识库是虚构的"星河咖啡"公司资料。Claude 不可能事先知道"星光值 300 点能换一杯美式"，它答得出来，就说明检索真的起作用了。

## 1. 加载文档

把 txt、md、pdf 统一读成纯文本。PDF 按页拆开，回答时可以引用到第几页。

实际项目里这一步往往最脏最累：扫描件要 OCR，表格要转换，网页要去掉导航栏和广告。**进来的文本质量，决定了后面一切的上限。**

→ `rag/loader.py`

## 2. 切块（Chunking）

**为什么切**：问题通常只和文档的一小段有关。切成小块，检索才能精确定位；向量模型的输入长度也有上限（bge-small 是 512 token）。

**怎么切**：本项目按句子边界切（句号、问号、换行等），一句句往块里加，快超过 `CHUNK_SIZE` 就收成一块。不在句子中间硬切，是为了让每块意思完整。

**为什么要重叠**：如果答案正好跨在两块的边界上，没有重叠就会被劈成两半。让下一块开头重复上一块末尾约 `CHUNK_OVERLAP` 个字，可以缓解这个问题。

**块大小怎么定**：

| 块太小 | 块太大 |
| --- | --- |
| 上下文不完整，一句话离开前后文可能看不懂 | 一块里混了好几个话题，向量被"平均"掉，跟哪个问题都不太像 |
| 检索精确，但给模型的信息碎 | 塞给模型的无关内容多 |

本项目用 `evaluate.py --compare` 实测过：BGE 在 300 字时，"积分能换什么"这题的正确片段掉到了第 7 名，因为那块同时包含会员等级、星光值获取、星光值兑换三个问答；改成 200 字后升到第 3 名。**块大小没有标准答案，要拿自己的数据测。**

→ `rag/chunker.py`

## 3. 向量化（Embedding）

把一段文字变成一串数字（向量），并且让**意思相近的文字，向量也相近**。这样"找相关内容"就变成了数学计算。

本项目实现了两种向量，可以对比着看：

### TF-IDF（手写，关键词向量）

- 每一维对应一个词，值 = 词频(TF) × 稀有度(IDF)；
- IDF = log(总块数 / 包含这个词的块数)：到处都出现的词（"的""员工"）区分度低，权重小；
- 中文没有空格，这里用"单字 + 相邻两字"近似分词；
- 向量维度 = 词表大小（本项目两千多维），绝大多数是 0，叫**稀疏向量**。

缺点：只认字面。问"积分"，文档里写的是"星光值"，它就找不到。

### BGE（神经网络，语义向量）

- `BAAI/bge-small-zh-v1.5`，输出 512 维**稠密向量**；
- 模型在大量"问题–相关段落"数据上训练过，能把同义表达映射到相近位置；
- BGE 的约定：**问题**前面加一句指令"为这个句子生成表示以用于检索相关文章："，文档不加。问题短、文档长，两者形式不对称，加指令能让问题向量更靠近答案段落。

运行 `python learn_rag.py`，默认问题"会员积分能换什么东西？"就是专门挑来对比两种向量的。

### 归一化与余弦相似度

两个向量的**余弦相似度** = 夹角的余弦，范围 [-1, 1]，越接近 1 越相似。如果先把所有向量缩放成长度 1（L2 归一化），余弦相似度就等于**点积**，算起来最快。本项目的两种向量都做了归一化。

注意不同向量的分数范围差别很大：BGE 相关内容一般 0.4–0.7，TF-IDF 一般 0.1–0.3。所以相似度阈值 `MIN_SCORE` 要按向量类型分开设。

→ `rag/embedder.py`

## 4. 存储与检索

"向量数据库"最朴素的形态就是一个 N×D 的矩阵：N 个块，每块 D 维。检索就是一行代码：

```python
scores = embeddings @ query_vector   # 和每一块算点积 = 余弦相似度
best = np.argsort(-scores)[:top_k]   # 取分数最高的 top_k 个
```

Chroma、Milvus、FAISS 这些专业向量库做的是同一件事，只是数据到了百万级以后，逐个比较太慢，它们用**近似最近邻（ANN）**索引（HNSW、IVF 等）牺牲一点精度换速度。几千块的知识库，numpy 完全够用。

**相似度阈值**：问"北京今天天气怎么样"，最相似的块也只有 0.31 分。不设阈值的话，这些无关片段也会被塞给模型。`MIN_SCORE` 把它们过滤掉，模型拿到空资料，就会老实回答"知识库中没有"。

→ `rag/vector_store.py`、`rag/pipeline.py` 的 `retrieve()`

## 5. 增强生成

把检索结果拼进 Prompt：

```
System：你是知识库问答助手。只依据 <documents> 里的资料回答；资料里没有就说没有；引用时标注编号 [1]。

User：<documents>
        <document index="1" source="星河咖啡会员与产品FAQ.md">……</document>
        <document index="2" source="……">……</document>
      </documents>
      问题：会员积分能换什么东西？
```

几个要点：

- **约束模型只用资料**：否则它会用自己的知识"补充"，私有场景下就是在编造；
- **允许说不知道**：明确告诉它资料不足时该怎么说，比事后检查有没有幻觉容易得多；
- **标注引用编号**：用户可以点开原文核对，答错了也能看出是检索的问题还是生成的问题；
- **用 XML 标签分隔资料和问题**：模型能清楚分辨哪些是参考资料、哪些是问题。

网页版每条回答下面都能展开"完整 Prompt"，看到实际发给 Claude 的内容。

→ `rag/generator.py`

## 6. 多轮对话：追问改写

用户问完"会员有哪些等级？"，接着问"最高那级有什么福利？"。直接拿后一句去检索，向量里没有"会员"这个信息，很可能检索失败。

解决办法是**查询改写**：检索前先让模型结合对话历史，把追问改写成完整问题："星河咖啡最高等级会员有什么福利？"。代价是多一次模型调用。

另外，对话历史只往后追加、不修改已经发出的内容。这样 Claude 的提示缓存能命中，也满足 API 对历史记录"只追加"的要求。

→ `rag/generator.py` 的 `rewrite_query()`，`rag/pipeline.py` 的 `Conversation`

## 7. 怎么判断 RAG 好不好

RAG 答错，原因无非两类：

1. **检索没找到**正确资料（最常见）；
2. 资料找到了，但**模型没用好**（理解错、遗漏、编造）。

所以评测也分两层。本项目实现了第一层，检索评测（`evaluate.py`）：

- **Hit@K**：正确片段出现在前 K 个结果里的问题占比。只有前 K 个会给模型看，排在后面等于没找到；
- **MRR**：正确片段排名倒数的平均值。排第 1 得 1 分，排第 2 得 0.5 分，越高说明排得越靠前。

改任何参数之前先跑一遍，改完再跑一遍，用数字说话，不要凭感觉。

注意：示例知识库只有二十几块，测试题也只有 12 道，在这个规模上 TF-IDF 和 BGE 的差距不明显，因为大部分测试题和原文用词相近。文档越多、用户的说法和原文差别越大，语义向量的优势越明显。可以往 `eval_questions.json` 里加一些"换个说法"的题目试试。

## 8. 进阶方向

学会了基础版以后，可以按兴趣继续改进：

| 方向 | 做法 | 解决什么问题 |
| --- | --- | --- |
| 混合检索 | TF-IDF/BM25 和向量检索的结果合并（如 RRF 倒数排名融合） | 语义检索对专有名词、编号、型号不敏感，关键词检索正好互补 |
| 重排序（Rerank） | 先粗召回 20 块，再用交叉编码器（如 bge-reranker）精排取前 4 | 向量检索快但粗，重排序慢但准 |
| 结构感知切块 | 按 Markdown 标题、段落切；每块开头加上所属标题 | 块的语义更完整，检索更准 |
| 父子块 | 用小块检索，命中后把它所在的大块交给模型 | 兼顾检索精度和上下文完整 |
| HyDE | 先让模型写一个假想答案，用假想答案的向量去检索 | 问题和答案长得不像时，答案和答案更像 |
| 生成评测 | 用模型给回答打分：是否忠于资料、是否回答了问题 | 评测第二层：模型有没有用好资料 |
| 换专业向量库 | Chroma / FAISS / Milvus | 数据量上到十万、百万块时 |

本项目的代码结构就是为这些改进留的：每一步一个文件，替换其中一步不影响其他部分。
